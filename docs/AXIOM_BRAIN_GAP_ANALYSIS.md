# Grace vs AXIOM-BRAIN: gap analysis

Read directly against `/Users/gagan/Git_projects/Grace` and `/Users/gagan/Git_projects/AXIOM-BRAIN` on 2026-08-06.

## Summary

These are genuinely different products with one shared organ, not the same product at different maturity levels. Grace's governance core — policy evaluation, Ed25519/ML-DSA-65 signing, RFC 6962 Merkle receipts, a live governed LLM/API gateway, and an agent execution loop (ReAct) — is more rigorous and more "real" engineering than AXIOM-BRAIN's equivalent code. AXIOM-BRAIN's governance layer (`govern/policy_evaluator.py`) literally contains a class called `DemoPolicyEvaluator` using `random.Random()` and canned deny-reason templates as its fallback path, and its "real" evaluator (`policy/evaluator.py` + `policy/dsl.py`) is a reasonable rule engine but simpler than Grace's. Where AXIOM-BRAIN wins decisively is everything oriented around being a "company brain": a knowledge graph with real OAuth connectors (GitHub/Linear/Slack/Notion/Gmail), an MCP server exposing passport-gated tools, entity/edge classification and clustering, and — the single biggest lift — a genuine Three.js 3D graph UI with bloom postprocessing and custom clustering layout. Grace has none of that; it was never meant to be a knowledge-graph product, and porting "everything AXIOM-BRAIN does" means bolting an entirely separate subsystem (ingestion + graph + 3D UI) onto Grace's receipts/governance product, not upgrading a stub.

## Grace has things AXIOM-BRAIN doesn't

- **Governed LLM/API gateway** (`apps/backend/src/axiom/gateway/`): a live reverse proxy in front of LLM providers (and arbitrary HTTP targets via `/v1/proxy/{target}`) that classifies every request, runs it through policy evaluation before forwarding, injects vault-backed credentials, and seals a signed receipt on success/failure/timeout — including for streaming responses (hashes the SSE stream as it flows through). This is a genuinely different capability from anything in AXIOM-BRAIN, which has no proxy/gateway layer at all. It's the piece that makes governance apply to *live* agent traffic rather than only to logged/observed actions after the fact.
- **Post-quantum signing** (`services/crypto/ml_dsa_65.py`, `hybrid_signer.py`): ML-DSA-65 (FIPS 204) support and hybrid Ed25519+ML-DSA signing. AXIOM-BRAIN only has classical Ed25519.
- **Merkle inclusion/consistency proofs** (`services/crypto/merkle.py`): full RFC 6962 Certificate-Transparency-style proof machinery, not just a linear prev/this hash chain.
- **Real agent execution** (`workers/react_loop.py`, `workers/agent_worker.py`): Grace runs agents end-to-end through its own gateway; AXIOM-BRAIN's `govern/agent_registry.py` and `agent_actions.py` only register and observe agent identities/actions from outside.

## Punch list: what porting "everything AXIOM-BRAIN does" into Grace requires

Ordered by (a) how central it is to AXIOM-BRAIN's "company brain" value prop and (b) how much foundation Grace already has.

1. **Knowledge graph core (`organize/` + `retrieval/`) — multi-week, no foundation.** This is the spine everything else in AXIOM-BRAIN hangs off (clustering, centrality, edge proposals, graph-ranked search). Grace has `services/embeddings/` (384-dim fastembed/OpenAI vectors) which is directly reusable as the embedding layer, but there is no entity/edge model, no classifier, no clustering, no graph-rank algorithm to build on. This is a from-scratch subsystem: new DB schema (entities, edges, clusters), new services, new API surface.

2. **Connectors (`connectors/`) — multi-week, no foundation.** Real OAuth integrations for GitHub/Linear/Slack/Notion/Gmail plus a sync runner and ingestion pipeline. Grace has OAuth plumbing for its own auth (`services/google_oauth.py`) that could be a starting template for the OAuth dance, but there's no connector registry, no per-service ingest/writer pattern, and no webhook/polling sync infrastructure beyond the single n8n callback. Each connector is itself real integration work (rate limits, pagination, incremental sync, schema mapping) — treat as N separate small-to-medium projects, not one.

3. **3D graph frontend (`Brain.tsx`, `BrainCanvas/`) — multi-week, no foundation.** Genuine Three.js scene with custom shaders/postprocessing (bloom), hex-grid background, cluster bracket labels, curved conduit rendering, camera easing. Grace's frontend has zero 3D/graph-visualization code or dependencies (no `three` in `apps/frontend/package.json`). This is pure new build, gated on #1 existing first (nothing to visualize without the graph).

4. **MCP server (`mcp/`) — small-to-medium, no foundation but Grace's building blocks fit well.** AXIOM-BRAIN's MCP server is mostly a thin FastMCP wrapper (`mcp/tools.py`) around existing passport/receipt primitives (`mcp/service.py` reuses `govern/passports.py` and `govern/receipts.py`). Grace already has stronger signing/receipt primitives than what AXIOM-BRAIN's MCP layer sits on — `services/crypto/`, `services/receipt/` — so this is largely "write a FastMCP tool layer over what Grace already has," not a new crypto/governance build. Realistic size: days to low weeks, mostly wiring plus deciding what to expose as MCP tools (governance verdicts? vault-scoped actions?).

5. **Skills system (`skills/`) — small-to-medium, partial foundation.** Executable signed `.md` skill files with a runner/registry. Grace has no skill-file concept, but it does have agent definitions (`services/agent_definitions/`), a real execution loop (`workers/react_loop.py`), and signing infra that a skill-file format could reuse directly. This is more "define a new artifact type and a loader" than a new execution engine — Grace already executes things.

6. **Everything else (govern/watchdog, security_health, cluster_checks, llm_keys) — small, mostly graph-dependent.** These AXIOM-BRAIN modules are largely monitoring/health-check layers over the graph and passport system. Not worth prioritizing independently; they fall out naturally once #1 (graph) and #4 (MCP passports) exist, since Grace's governance/policy stack is already more capable than what these modules check against in AXIOM-BRAIN.

**Not needed / already exceeded:** policy evaluation, signing (Ed25519 + PQC), Merkle receipts, vault, and agent execution. Do not spend time "catching up" here — Grace's implementations are more rigorous than AXIOM-BRAIN's in all five, and AXIOM-BRAIN's policy evaluator has a demo/mock fallback path that Grace's does not.
